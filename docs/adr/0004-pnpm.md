# ADR 0004 — pnpm as the package manager

- **Status:** Accepted
- **Date:** 2026-10-22
- **Phase:** improvement_v2, Phase 0 (environment) and Phase 1 (safety net)
- **Supersedes:** nothing

## Context

The repository had two lockfiles: a stale `package-lock.json` from npm and a canonical `pnpm-lock.yaml`. That is a predictable source of "works on my machine" failures:

- a contributor running `npm install` could resolve a different dependency graph from the one CI used;
- a dependency update might change one lockfile and not the other;
- the Node version was not pinned in the repository, so local and CI installs could differ.

The project also runs on a constrained development host and in GitHub Actions. Install speed and disk usage are practical concerns, not only preferences. Several packages have install scripts, which are a supply-chain surface that should be explicitly reviewed rather than silently executed.

## Decision

Use **pnpm 12** as the only package manager.

1. **Pin the toolchain.** `package.json` declares `"packageManager": "pnpm@12.14.0"` and requires Node.js 24 or newer and pnpm 12 or newer. `.nvmrc` records the Node major version used locally and in CI.
2. **Keep one lockfile.** `pnpm-lock.yaml` is committed. `package-lock.json` is removed. Installation in CI uses `pnpm install --frozen-lockfile`.
3. **Allow build scripts explicitly.** `pnpm-workspace.yaml` lists the packages whose install scripts are trusted (`esbuild` and `unrs-resolver` in the current graph). A new dependency with an install script requires a deliberate change to that list.
4. **Use pnpm in documentation and CI.** README commands, contributor commands, the checks workflow and the Pages deployment all use the same pnpm version.

Corepack is the recommended bootstrap path (`corepack enable`), because it reads `packageManager` and downloads the pinned version. A global `npm install --global pnpm@12` is documented as a fallback.

## Consequences

### Good

- Local development and CI resolve the same dependency graph.
- One lockfile means one place to review dependency changes.
- The `packageManager` and `engines` fields make the expected toolchain explicit instead of relying on tribal knowledge.
- Trusted install scripts are visible in version control.
- pnpm's content-addressed store reduces repeated downloads, which matters on small development machines and in cache-enabled CI.

### Bad

- Contributors who only have npm must install pnpm or enable Corepack first.
- The pinned pnpm major version must be updated deliberately. Renovation is a toolchain decision, not an incidental lockfile change.
- A dependency that needs an install script will not build until it is added to the allowlist, which can look like an obscure failure to a first-time contributor.
- The GitLab mirror and GitHub repository must both receive the lockfile change; there is still one canonical workflow.

### Neutral

- The repository is a single package, not a workspace with multiple publishable packages. `pnpm-workspace.yaml` exists for the build-script policy, not for package linking.
- `pnpm-lock.yaml` is large in the diff. That is expected for the single source of dependency truth.

## Alternatives considered

**Stay on npm.**

Rejected. It was the original state, and the stale dual-lockfile problem was already causing confusion. npm is perfectly workable, but changing package managers later would be a larger disruption than standardising now.

**Use Yarn or Bun.**

Rejected. Neither offered a benefit that justified a second migration. The project already had a pnpm lockfile and CI was moving to pnpm.

**Commit both lockfiles "for compatibility".**

Rejected. Two lockfiles reintroduce the drift this decision is meant to remove. There is no supported second installation path.

**Disable install scripts globally.**

Rejected. esbuild needs its native binary, and silently skipping the script produces a confusing failure. An explicit allowlist keeps the supply-chain decision visible.
